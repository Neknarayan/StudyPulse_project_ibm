## 1. Problem Statement
In many colleges, a student who is falling behind is noticed only after poor exam results, when there is little time left to help. Teachers handle large classes and cannot manually track every student's attendance, assignments and study habits. This delays support and contributes to failures and dropouts, which works against **SDG 4 (inclusive and equitable quality education)**.

## 2. Proposed Solution
StudyPulse is an early-warning web application. It takes routine student indicators, uses a machine-learning model to estimate each student's probability of failing, groups students into **High**, **Medium**, and **Low** risk, and shows teachers which factors drive the risk together with a suggested support action. A what-if predictor lets a teacher test how changes (for example, better attendance or study hours) affect risk.

## 3. Objectives
- Predict which students are at risk of failing using data available before exams.
- Rank students so teachers can prioritise limited time.
- Explain every prediction in plain language instead of showing a bare score.
- Suggest practical, human-reviewed support actions.
- Deliver the system as an easy-to-run web prototype.

## 4. Data
Nine input features are used:
1. `study_hours_week`: Weekly study hours
2. `attendance_pct`: Attendance percentage (0–100%)
3. `prev_grade`: Previous grade (0–20 scale)
4. `absences`: Total absences
5. `past_failures`: Number of past failures (0–3)
6. `assignment_pct`: Assignment completion rate (0–100%)
7. `sleep_hours`: Average sleep hours per day
8. `parental_support`: Parental support rating (1–5)
9. `internet_access`: Home internet access (0/1)

The target is a binary `at_risk` label. For this prototype, the data is synthetic: 600 records generated by `src/data_gen.py` with realistic relationships and random noise (about 36% at risk), so the project runs offline and contains no real student information. The pipeline accepts any real dataset with the same columns.

## 5. Methodology
1. **Data Ingestion:** Generate/load the dataset and validate columns.
2. **Exploratory Data Analysis:** Analyze how attendance, grades, study time, and past failures relate to academic risk.
3. **Data Splitting:** Stratified 80/20 train-test split (480 train, 120 test).
4. **Model Training:** Standardise features with `StandardScaler` and train Logistic Regression (balanced class weights) alongside Random Forest Classifier for benchmark comparison.
5. **Model Evaluation:** Evaluate using Accuracy, Precision, Recall, F1-Score, and ROC-AUC, plus 5-fold cross-validation.
6. **Explainability:** Deploy Logistic Regression because its linear coefficients enable per-student local explanations ($\text{coefficient} \times \text{standardised value}$).
7. **Actionable Recommendations:** Map top risk-raising factors to rule-based pedagogical support suggestions.
8. **Web Delivery:** Serve results through a Flask web application with a responsive dashboard and interactive predictor.

## 6. System Workflow
$$\text{Student records} \longrightarrow \text{Cleaning \& Scaling} \longrightarrow \text{Model Scoring} \longrightarrow \text{Risk Level} \longrightarrow \text{Explanation \& Suggested Support} \longrightarrow \text{Teacher Review}$$

- **High Risk:** $\ge 60\%$ probability of failing
- **Medium Risk:** $35\% - 60\%$ probability
- **Low Risk:** $< 35\%$ probability

## 7. Results on the Prototype Dataset
Held-out test results (synthetic dataset of 600 records):

| Model | Accuracy | Precision | Recall | F1-Score | ROC-AUC |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **Logistic Regression (Deployed)** | **0.708** | **0.571** | **0.744** | **0.646** | **0.796** |
| Random Forest | 0.767 | 0.703 | 0.605 | 0.650 | 0.822 |

- **5-fold cross-validated F1 for Logistic Regression:** $0.632 \pm 0.023$.
- Random Forest scores slightly higher on precision and AUC, but **Logistic Regression was kept for deployment** because it has higher recall (misses fewer at-risk students) and provides transparent, interpretable explanations.

## 8. Innovation
Rather than stopping at a black-box prediction, StudyPulse turns the model into an actionable intervention tool:
- Prioritised contact list so educators focus where need is greatest.
- Plain-language explanation for every flag.
- Suggested proactive intervention tailored to the specific risk driver.
- Simple and explainable architecture building educator trust.

## 9. Ethics and Responsible Use
- **Decision Support:** Predictions support teachers; they never replace human judgement or decide academic outcomes autonomously.
- **Privacy & Security:** Anonymised student IDs, role-based access control, and secure data storage.
- **Fairness:** Prior to real deployment, audit for disparate error rates across demographic subgroups; do not use protected attributes.
- **Support-Oriented:** Flagged students should receive positive help and guidance, not punitive labels.

## 10. Limitations
- The prototype is trained and tested on synthetic data; real-world accuracy must be validated on consented, institutional datasets.
- Current models process a single snapshot rather than longitudinal time-series data.
- Support suggestions are rule-based and general.

## 11. Future Scope
- Validate on real anonymised institutional data across multiple semesters.
- Incorporate time-series attendance and quiz trends.
- Fairness and algorithmic bias audits.
- Feedback loop where educators record intervention outcomes to refine models.
- Automated LMS (Learning Management System) integration with email/SMS alerts.

## 12. Conclusion
StudyPulse proves how routine academic indicators can be converted into an early, explainable warning that empowers educators to intervene before failure occurs. Aligned with **SDG 4**, it aims to reduce preventable course failures and dropouts through data-informed educational support.
